# AHT20 I2C address, status and preparation evidence

Use this only for the confirmed AHT20 protocol. Board routing, adapter identity, module supply/signals, current address ownership and the application's execution user are separate prerequisites. A sensor supply range is not permission to use that voltage on a module or board signal.

## Address byte is not a command

The manufacturer's V1.1 page 8, §5.3 and timing diagram, shows a 7-bit address followed by a separate R/W bit. Read the §5.4 phrase "send 0x71" in that context:

| Meaning | Value | Linux userspace interpretation |
|---|---|---|
| Seven-bit slave address | `0x38` | Set through I2C_SLAVE or the message address |
| On-wire write address | `(0x38 << 1) + 0 = 0x70` | Generated by the adapter; not payload |
| On-wire read address | `(0x38 << 1) + 1 = 0x71` | Generated by the adapter; not payload |
| Status byte | One returned byte | Read directly; no `0x71` payload first |

For i2c-dev, set `I2C_SLAVE` to `0x38`, then read one byte. `write(0x71); read(1)` is not this status operation. If current wiring/ownership and actual-user permissions are confirmed and this device access is authorized, the corresponding single read message in a compatible `i2ctransfer` is:

```sh
: "${bus:?Set the verified current adapter number}"
i2ctransfer -y "$bus" r1@0x38
```

Do **not** write `w1@0x38 0x71 r1` for that operation. A transaction containing `w1` writes payload even if its purpose is called a "check". No `-f`, blind scanning, reset or initialization is needed merely to list preparation gaps. A device read is still an active transaction, not passive metadata.

## Keep status, conversion and acceptance separate

Status bit3 indicates calibration enabled and bit7 indicates busy; arbitrary returned values/ACK alone do not uniquely identify a sensor. Initialization (`BE 08 00`, when required by the calibration state) and conversion trigger (`AC 33 00`) are **writes**, not status queries. They are outside a metadata-only request. For an actual reader, follow the manual's timing, bounded busy wait and independent complete-frame CRC before decoding; do not reuse stale samples after error. Do not transfer these opcodes to AHT10/AHT21 or another chip without its own evidence.

A command review needs the reviewed transaction, a justified replacement and evidence limits; do not append initialization, conversion or reset command sequences that the user did not request. An undocumented payload has unknown effects: do not guess that it is ignored, harmless or guaranteed not to change state.

A missing registered `N-0038` entry means only that the snapshot lists no such kernel client. Different registered addresses (such as 0x22 and 0x51) do not prove 0x38 has no other user or race; do not conclude "no conflict", "no driver contention" or "direct access is safe" from that list. Keep current ownership unresolved where unobserved, check it before an authorized request, and stop on busy/permission/I/O errors without force. It does not establish address availability, no previous response, or permission for the current user. "No response captured" is different from "sensor never responded". Root discovery cannot establish service/container access, and a status read cannot establish temperature/humidity accuracy, circuit loading, pullup/timing margins or calibrated supply voltage.

For **preparation-only** requests, keep actual-user/node access and physical measurements unknown when absent; the minimal next step may be the existing project's runtime identity/node permissions rather than a bus transaction. Do not summarize a single remaining gap (whether "only application access" or "only voltage/ACK") while other unmeasured physical/functional conditions remain unknown. `id`, node listings and `test -r/-w` predict permissions only: success is not a real open, API transaction or application-access acceptance. State the limited conclusion and next authorized step, keeping the original access fact unknown. A resistor supplying a SoC power domain is not a resistor in the SDA/SCL signal path; preserve the selected pin's actual route. Do not infer module pullups, combined resistance or timing margins from a hypothetical module.
